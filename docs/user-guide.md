# 사용자 가이드

> NScouter — Scouter APM 모던 클라이언트.
> 이 문서는 **쓰는 법**을 다룬다. 빌드·개발은 [개발 가이드](dev-guide.md), 배포는 [배포 가이드](deploy-guide.md).

## 1. 접속

앱을 켜면 상단 바에 접속 폼이 있다.

| 칸 | 값 |
|---|---|
| Host | 콜렉터 주소 (예: `127.0.0.1`) |
| Port | 콜렉터 TCP 포트 (기본 `6100`) |
| User / Password | 콜렉터 계정 |

**자동 연결**을 켜면 다음 실행부터 이 정보로 바로 붙는다.
다만 **비밀번호가 `config.json` 에 평문으로 저장된다** — 공용 PC 에서는 켜지 말 것.
끄면 저장돼 있던 비밀번호도 함께 지워진다.

붙었는지는 상단 왼쪽 배지(초록 점 + 서버 이름)로 안다. 끊을 때는 `연결 해제`.

---

### 1.1 서버를 여러 개 두고 갈아타기

운영·QA 처럼 콜렉터가 여럿이면 매번 호스트와 계정을 다시 칠 것 없이 **골라서 옮긴다.**
접속에 성공한 서버는 자동으로 목록에 남고, 헤더의 서버 버튼(▾)에서 고른다.

- **한 번에 한 서버다.** 두 콜렉터를 나란히 보는 것이 아니라 빠르게 옮겨 가는 기능이다
- 갈아타면 **화면이 새로 시작한다** — 오브젝트 해시가 서버마다 달라 필터·상세 탭을
  그대로 둘 수 없다. 창 크기·글자 크기 같은 설정은 그대로다
- 목록에는 `host:port · 계정` 이 함께 보인다. 이름만으로는 운영과 QA 를 못 가른다
- **비밀번호는 «자동 연결» 을 켠 서버만 저장된다**(config.json 에 평문). 저장 안 한 서버는
  목록에 «비밀번호 물음» 이라고 적히고, 고르면 접속 폼에 호스트·계정이 채워진 채로
  비밀번호만 묻는다
- `✕` 로 목록에서 지운다. 지워도 접속 정보만 사라질 뿐 서버는 그대로다

## 2. 화면 구성

```
┌ 상단 바 ─ 서버 배지 · XLog / Active / Visualize / Counter / Alert 탭 · 알림 배지 · 설정(⚙)
├ 왼쪽 SERVICES ─ 붙어 있는 오브젝트(에이전트) 목록
└ 본문 ─ 선택한 탭
```

**왼쪽 목록의 클릭은 두 가지다.**

| 조작 | 결과 |
|---|---|
| 왼쪽 클릭 | 그 오브젝트를 보기에 넣는다 (여러 개 고를 수 있다). **아무것도 안 고르면 아무것도 안 그린다** — 차트에 «왼쪽에서 볼 서버를 고르세요» 가 뜬다 |
| **오른쪽 클릭** | 그 오브젝트의 상세 메뉴 — 속성·스레드·힙·설정 등 (→ [6장](#6-오브젝트-들여다보기)) |

목록 머리의 `N대 선택 · 해제` 를 누르면 선택이 풀린다. 묶음 머리의 체크 칸은 그 묶음을 통째로 고른다.

**고르기는 XLog 탭마다다**(3.0). 목록은 지금 XLog 탭(나눠 띄웠으면 지금 판)의 고르기를 보여 주고 고친다.
Active · Counter · Visualize 는 지금 XLog 탭의 고르기를 따른다.

이름 앞의 **색 칸**은 그 서버의 XLog 점·카운터 선 색이다 — 범례 노릇을 한다
(트랜잭션을 내는 tomcat 같은 javaee 오브젝트에만 붙는다). 그 앞의 둥근 점은 살아 있는지다.
짧은 이름이 겹치면 부모를 붙여 적는다 — 앱마다 `HikariPool-1` 인 커넥션 풀은
`order-app · HikariPool-1` · `shop-app · HikariPool-1` 로 나온다.

**목록은 타입으로 묶여 있다.** 묶음 머리를 누르면 접힌다 — 접혀 있어도
`살아있는 수/전체` 는 보인다. 위의 찾기 칸은 **이름과 타입 둘 다** 뒤지므로
`CJFW`(시스템)로도 `BO`(이름 일부)로도 찾는다. 이름은 짧은 이름이 아니라
전체 경로로 보기 때문에 `/PRD-FSCP/` 같은 중간 마디로도 걸린다.
찾는 동안에는 접어 둔 묶음도 펼쳐진다.

## 2.1 SERVICES 목록 — 묶기

오브젝트가 백 개를 넘으면 평평한 목록에서는 찾을 수가 없다. 세 가지로 묶을 수 있다.

| 묶기 | 기준 | 예 |
|---|---|---|
| `타입` | 오브젝트 종류 (`obj_type`) | tomcat · datasource · linux |
| `그룹` | 이름의 **첫 마디(호스트)** | `/CJFW` · `/order-app` |
| `서비스` | **논리 서비스** — 한 서비스가 여러 대로 뜨는 곳 | `SAFS` (Task 4대) |

Scouter 의 이름 규칙이 `/{host}/{name}` 이라 첫 마디가 호스트다
(ASIS 도 같은 자리를 잘라 호스트를 찾는다). **앱과 그 앱의 datasource 가 한자리에 모인다** —
`/order-app/order-app` 과 `/order-app/order-app/HikariPool-1` 이 같은 `/order-app` 이다.

**두 기준은 서로를 대신하지 못한다.** 타입은 「무엇인가」, 그룹은 「어느 호스트에 있는가」다.
운영에서 `obj_type` 에 시스템 이름을 넣어 쓰면(CJFW · PRD-ORD) 둘이 비슷해 보이지만,
그때도 나누는 결이 다르다.

- 고른 기준은 **껐다 켜도 남는다**
- 검색은 기준과 무관하게 이름 전체 경로와 타입 둘 다 본다
- 마디가 하나뿐인 이름(`test-host`)은 `(그룹 없음)` 으로 모인다

### 서비스로 묶기 — ECS · 쿠버네티스

한 서비스가 Task 여러 개로 뜨는 곳에서는 이름을 Task 마다 다르게 지어야 하고
(안 그러면 콜렉터가 한 대로 본다 — [이름 중복 가이드](duplicate-objname-guide.md)),
그러고 나면 **같은 서비스가 여러 줄로 흩어진다.** `서비스` 묶기가 그걸 다시 모은다.

```
SAFS                        3
 ├ ip-10-75-113-103...
 ├ ip-10-75-113-183...
 └ ip-10-85-60-123...
```

- **서비스 마디를 고르면 속한 Task 전부**를 합쳐 조회한다
- 펼쳐서 **특정 Task 만** 고를 수도 있다. 그러면 그 서비스는 더 이상 자동으로 안 따라간다
  — 「지금 이 Task 들」 을 보겠다는 뜻이기 때문이다
- **Task 가 뜨고 져도 저절로 따라간다.** 명단을 들고 있지 않고 이름에서 매번 다시 푼다
- 고른 서비스에 **살아 있는 Task 가 하나도 없으면** 그렇게 말해 준다
  (「안 골랐다」 와 다른 일이다)

묶는 기준은 **태그 > 이름 규칙** 순이다. 사이트의 이름 규칙이 다르면
**설정 → 서비스 묶기**에서 고친다 — 거기서 지금 붙어 있는 서버로 몇 개가 묶이는지
바로 보여 준다.

**한 대짜리는 묶지 않는다.** 묶을 것이 없는데 마디를 만들면 깊이만 한 겹 는다.

**서비스로 묶어 보는 동안은 색도 서비스가 정한다.** 같은 서비스의 Task 는 색 칸·XLog 점·카운터 선이
모두 한 색이다 — Task 마다 색을 주면 4대짜리 서비스가 네 색으로 흩어지고, 재배포할 때마다 색이 바뀐다.
서비스에 안 속한 서버는 원래 색 그대로다. 다른 묶기로 돌아가면 서버마다 색으로 돌아간다.

### 비활성 정리

콜렉터는 내려간 서버를 스스로 지우지 않는다. Task 가 자주 갈리는 곳에서는 목록이 계속
늘어나므로, 죽은 것이 있으면 목록 머리에 **「비활성 정리 N」** 이 나온다(없으면 안 나온다).
**설정 → 비활성 자동 정리**에서 주기로 돌릴 수도 있다 — 끄기(기본) · 30분 · 1시간 · 6시간.

※ **정리는 콜렉터 전역이다.** 같은 서버를 보는 다른 사람 화면에서도 사라진다.
그래서 자동은 기본이 꺼져 있다.

※ 이 앱의 자동 정리는 **앱이 켜져 있을 때만** 돈다. 콜렉터가 스스로 지우게 하려면 콜렉터 플러그인을
쓴다 — [이름 중복 가이드](duplicate-objname-guide.md) 「콜렉터에서 자동 정리」.

**죽은 것은 접혀 있다.** 묶음마다 살아 있는 것만 보이고 죽은 것은 `▸ 죽은 N개` 한 줄로 접힌다.
눌러 펼친다. 묶음 머리의 `살아 있는 수/전체` 는 그대로라 «하나가 내려갔다» 는 접어도 보인다.
검색 중이거나, 골라 둔 것(과거 구간에서 고르기에 들어간 죽은 Task)은 접지 않는다.

골라 둔 서비스의 Task 가 정리로 목록에서 다 빠져도 **그 서비스 마디는 남는다**
(`목록에 Task 가 없습니다` 와 함께). 거기서 체크를 풀면 된다.

## 3. XLog 탭 — 트랜잭션 보기

### 3.0 툴바 · 탭 · 화면 나누기

**툴바** 첫 줄은 자주 바꾸는 것이다 — `실시간/과거` · `에러만` · `서비스` · `IP` · `조건 더보기` · `필터`,
그리고 오른쪽 끝에 파란 **`트랜잭션 찾기`**(3.5.1).
한 번 정하면 잘 안 바꾸는 것은 `조건 더보기` 안에 있다 — `Y축` · `범위` · `저장본` · `Y최대` · `밀집` · `응답`.
더보기 안의 거름(응답·밀집)이 걸려 있으면 버튼에 그 수가 붙고, 켤 때 펼쳐진 채로 시작한다.

**탭**은 같은 화면을 다른 조건으로 띄운다. 툴바 위 `+ 탭` 은 **지금 탭을 복제**한다 —
날짜나 서버만 바꿔 견주는 데 쓴다. 탭마다 따로인 것: 모드·구간·차트 설정·거름·**고른 서버**.

- **이름 바꾸기** — 탭을 두 번 누르고 Enter (Esc 는 물림). 비우고 정하면 조건에서 만든 이름
  (`실시간`, `10/19 14:00~15:30`)으로 돌아간다. 안 붙인 이름이 겹치면 `실시간 2` 처럼 순번이 붙는다
- 탭은 최대 6개다 — 탭마다 받은 것을 따로 들고 있다

**화면 나누기** — 탭을 차트 위로 끌어 놓는다 (브라우저·편집기의 분할 보기와 같다).

| 놓는 자리 | 결과 |
|---|---|
| 판의 왼쪽 · 오른쪽 · 위 · 아래 가장자리 | 그 판 옆에 새 판으로 선다 (놓일 자리가 미리 칠해진다) |
| 판의 가운데 | 그 판을 그 탭으로 바꾼다 |

- 판은 최대 4개. 둘이면 경계를 끌어 몫을 바꾸고, 셋·넷은 2×2 다
- **판을 누르면 그 판이 지금 판이다** — 툴바·왼쪽 목록·아래 트랜잭션 표가 그 판의 것이 된다. 지금 판은 테두리가 진하다
- 판 머리의 `✕` 는 **판만 내린다** — 탭은 탭 줄에 남는다. 탭 줄에서 안 띄운 탭을 누르면 지금 판 자리에 뜬다
- 휠·Ctrl+휠은 커서 아래의 판을 고친다
- 나눈 배치는 껐다 켜도 남는다

**새 창으로 떼기** — 모니터 여러 대에 XLog 를 나눠 띄울 때. 브라우저 탭처럼:

- 탭을 **창 밖으로 끌어 놓으면** 그 자리에 새 창으로 뜬다 (다른 모니터에 놓으면 그 모니터에)
- 탭 오른쪽 클릭 → `새 창으로 떼기`, 또는 판 머리의 `↗`
- **뗀 창은 그 자체로 XLog 화면이다** — 왼쪽 서버 목록 · 툴바 · 탭·화면 나누기 · 트랜잭션 목록 · 상세를
  그 창에서 다 한다. 메인 창과 따로 고르고 따로 본다
- 뗀 탭은 메인 창 탭 줄에서 빠진다(그 창의 탭이 된다). 뗀 창에서 또 떼면 창이 하나 더 생긴다
- 되돌리기: 뗀 창 오른쪽 위 `메인 창으로 합치기`(그 창의 탭이 전부 메인 창으로), 또는 탭 오른쪽 클릭 →
  `메인 창으로 보내기`(그 탭만)
- 뗀 창을 **닫으면 그 창의 탭은 메인 창으로 돌아온다** — 실수로 닫아도 조건을 잃지 않는다.
  탭을 없애려면 탭의 `✕` 로 닫는다
- 접속·서버 전환·Counter/Active/Visualize/Alert·설정은 메인 창에서 한다. 메인 창을 닫으면 앱이 끝난다
- **껐다 켜면 뗀 창들이 같은 자리·크기로 다시 열린다**(탭·고르기도 그대로)
- 창이 여럿이어도 실시간 스트림은 하나다 — 창마다 고른 서버를 합쳐 받고, 창마다 제 서버만 그린다

### 3.1 실시간 / 과거

| 모드 | 쓰임 |
|---|---|
| **실시간** | 지금 들어오는 트랜잭션이 오른쪽에서 흘러 들어온다 |
| **과거** | 시각 두 개를 정하고 `조회` — 지난 구간을 그대로 본다 |

과거 모드에서는 차트 위에서:

- **휠** — 커서를 고정한 채 확대·축소
- **Shift + 휠** — 시간축 이동

이미 받아 온 구간 안이면 다시 조회하지 않는다.

**서비스로 묶어 고른 채 과거를 보면 그때 돌던 Task 까지 찾는다.** 실시간은 지금 살아 있는
Task 만 묻지만, ECS 처럼 그 사이 재배포가 있었으면 어제의 Task 는 하나도 안 남아 있다.
과거 모드에서는 지금 목록 · 그날 콜렉터 기록 · 이 앱이 본 기록을 합쳐 그 서비스의 Task 를
전부 넣는다 — 「비활성 정리」 로 목록에서 지운 Task 도 들어간다. 서버 목록 머리의
`N대 선택` 이 실시간보다 크게 나오는 것이 그래서다.

**이 앱이 본 기록은 껐다 켜도 남는다.** Task 가 언제 보였고 언제까지 살았나를 서버마다
`{데이터 폴더}/object-history/{호스트}_{포트}_{server_id}.json` 에 1분마다 남기고, 다시 붙을 때
되살린다. 최근 7일 안에 살아 있던 것을 최근 것부터 5,000건까지 남긴다. 되살린 Task 는 «죽은 것» 으로
시작한다 — 지금도 살아 있으면 다음 목록(10초)이 살린다.

**실시간에서도 왼쪽은 과거로 채운다.** 스트림은 «지금부터» 만 주므로, 예전에는 켜자마자
보이는 것이 오른쪽 끝 한 줄뿐이고 30분 창이 차려면 30분을 기다려야 했다. 이제는 접속하고
2초쯤 뒤에 **창의 왼쪽(아직 못 받은 과거)을 따로 받아** 채운다 — 몇 초에 걸쳐 왼쪽부터
차오르며, 그동안 차트 위에 `과거 구간 채우는 중… N건` 이 뜬다.

- 창을 넓히면(5분 → 30분) **늘어난 만큼만** 받는다.
- 왼쪽에서 서버를 **새로 고르면** 그 서버만 창 전체를 받는다. 이미 보던 서버는 다시 받지 않는다 —
  겹쳐 받으면 같은 트랜잭션이 두 번 그려진다.
- 뺐다 다시 고른 서버는 **뺀 동안의 구멍이 남는다.** 그 구간을 봐야 하면 과거 모드로 조회한다.
- 자정을 걸친 구간은 채우지 않는다(콜렉터가 날짜별로 담는다). 자정 직후에는 그날 것만 찬다.

### 3.2 Y축과 범위

`Y축` 은 점의 높이를 무엇으로 볼지다 — `Elapsed(sec)` · `CPU(ms)` · `SQL Time(sec)` · `SQL Count` ·
`ApiCall Time(sec)` · `ApiCall Count` · `Heap Used(KB)` (에이전트가 기본으로 안 재서 켜기 전에는 전부 0 — 3.6 속성 참고).
`범위` 는 가로축이 담는 시간(1·5·10·30분)이다. 둘 다 `조건 더보기` 안에 있다.

### 3.2.1 「3초짜리가 왜 맨 밑에 있지」

**Y축이 Elapsed 가 아니면 점 높이는 응답시간이 아니다.** 예를 들어 Y축이 `SQL Time` 일 때,
다른 앱을 6초 기다렸지만 SQL 은 한 건도 안 쓴 요청은 **0 에 찍힌다.** 맞는 그림이다.

그래서 Y축이 Elapsed 가 아닐 때는 **트랜잭션 목록에 그 축의 값을 한 칸 더** 보여준다:

```
URL                      ELAPSED    SQL Time
/shop/lab/slow<GET>      6,006ms    0ms       ← 6초 걸렸지만 SQL 은 0
```

두 수가 한 줄에 있어야 「왜 밑에 있나」가 아니라 「SQL 을 안 썼구나」로 읽힌다.
축 이름이 툴바와 차트 오른쪽 위에 적혀 있어도, 숫자 하나만 보이면 그게 점 높이인 줄 안다.

### 3.2.2 세로축이 낮으면 큰 점은 **한 개도 안 보인다**

점의 자리는 «값 ÷ 축 최대» 로 정해진다. 축보다 큰 값은 그림 밖으로 나가 **그려지지 않는다** —
현장에서 «30초짜리 타임아웃이 확인이 안 된다» 가 나온 것이 이것이다(기본 축이 9초였다).

- **축보다 큰 값은 맨 위에 붙는다.** 사라지지 않는다 — 다만 그 줄의 높이는 값이 아니다
- 그런 점이 있으면 맨 윗줄에 **옅은 띠**가 깔리고 왼쪽 위에 **`▲ N (축 위)`** 가 뜬다.
  «여기는 눈금이 아니다» 는 표시다 — 축을 올리면 제 높이로 흩어진다
- 축은 **사람이 정한다.** 툴바의 `Y최대` 에서 1·3·5·9·30·60·300초.
  데이터에 맞춰 자동으로 늘리지 않는다 — 튀는 것 하나에 축이 늘어나면 나머지가
  바닥에 깔려 서로 구별되지 않는다
- **Ctrl+휠**로도 늘리고 줄인다. 실시간에서도 된다 — 시간축(휠·Shift+휠)은 과거 구간
  전용이지만 세로축은 늘 움직인다

### 3.3 필터

필터는 **점과 목록에 함께** 걸린다. 구간을 골라 둔 뒤 필터를 바꿔도 목록이 바로 다시 걸러진다 —
조건을 풀면 빠졌던 것이 돌아온다. 다만 `트랜잭션 찾기`(3.5.1) 결과는 그 창의 조건으로 서버가 거른 것이라
툴바 필터를 다시 걸지 않는다.

| 필터 | 설명 |
|---|---|
| 에러만 | 실패한 트랜잭션만 |
| 응답 `이상` / `미만` + 초 | 예) `이상 2` = 2초 이상. 빈 칸이나 `0` 이면 조건 없음 — `조건 더보기` 안 |
| 서비스 | URL 의 일부 (예: `orders`) — 툴바 첫 줄 |
| IP | 호출자 IP 의 일부 (예: `10.89.`) — 툴바 첫 줄 |

**`이상`/`포함` 을 누르면 `미만`/`제외` 로 뒤집힌다.**
`IP 제외 10.89.2.17` 이면 그 IP **만 빼고** 보이고, `응답 미만 2초` 면 2초 **미만**만 보인다.
각 칸 오른쪽 `✕` 로 그 조건만 지운다.

### 3.3.1 조건 여러 줄 — `필터` 창

툴바의 서비스·IP 칸은 **한 줄짜리 뷰**다. 운영에서 하는 말은 «이 두 URL 만» 이거나
«헬스체크·모니터링은 빼고» 라서 한 칸으로는 안 된다. 툴바의 `필터` 를 누르면 창이 열린다.

규칙은 하나다 — **자리 안에서는 OR, 자리끼리는 AND**.

| 걸어 둔 것 | 뜻 |
|---|---|
| 서비스 포함 `/shop/order` + 포함 `/shop/cart` | 둘 **중 하나**면 통과 |
| 서비스 제외 `/health` + 제외 `/monitor` | 둘 **중 하나라도** 맞으면 뺀다 |
| 서비스 포함 `/shop` + 제외 `/cart` | `/shop` 중에서 `/cart` 만 뺀다 (제외가 세다) |
| 서비스 포함 `/shop` + IP 포함 `10.89.` | **둘 다** 만족해야 통과 |

- 툴바 칸은 각 자리의 **첫 줄**을 고친다. 창에서 세 줄을 걸어 두고 툴바에서 글자를
  고쳐도 나머지 줄은 그대로 있다. 툴바의 `필터 +N` 은 칸에 안 보이는 줄 수다
- **빈 줄은 조건이 아니다.** `+ 제외` 를 눌러 생긴 빈 줄이 전부를 지우지 않는다
- 응답시간(이상/미만)과 «에러만» 도 창에서 함께 건다
- **대상 서버는 창에서 바꾸지 않는다** — 왼쪽 SERVICES 목록이 그 일을 한다.
  두 곳에서 같은 것을 바꾸면 어느 쪽이 이겼는지 알 수 없다
- 걸어 둔 조건은 껐다 켜도 남는다(7.2)

#### 자주 쓰는 조건 담아 두기

장애를 볼 때 거는 조건은 매번 새로 짜는 것이 아니라 «결제만»·«헬스체크 빼고»처럼
몇 벌이 돌아가며 쓰인다. 창 아래에서 **이름을 붙여 담아 둔다.**

- 목록에서 이름을 누르면 **조건만** 얹힌다. **대상 서버는 그대로다** —
  서버 해시는 콜렉터마다 달라, 담아 둔 것에 서버까지 넣으면 다른 서버에서 불러왔을 때
  아무것도 안 걸린다
- 지금 걸린 조건과 같은 것에는 `●` 가 붙는다. 목록만 봐서는 무엇이 걸려 있는지 모른다
- 같은 이름으로 담으면 **덮어쓴다**. 버튼이 «덮어쓰기» 로 바뀌어 미리 말해 준다
- 불러오면 이름칸이 채워진다 — 고쳐서 같은 이름으로 다시 담는 흐름이 잦다

### 3.4 구간을 골라 목록으로

차트에서 **드래그**하면 그 사각형 안의 트랜잭션이 아래 표에 나온다.
시간 · 서버 · URL · IP · 응답시간 순이고, 행을 누르면 오른쪽에 상세가 열린다.

- **열 너비는 머리의 경계선을 끌어 바꾼다.** 끄는 선이 커서를 따라온다 — URL 은 남는 자리를
  다 쓰는 열이라, URL 오른쪽 경계를 왼쪽으로 끌면 IP 가 넓어진다. 경계를 **두 번 누르면** 그 열이
  기본 너비로 돌아간다. 정한 너비는 껐다 켜도 남는다(떼어 낸 창에서 바꾼 것은 그 창에서만)
- 머리를 누르면 그 열로 정렬한다

### 3.5 프로파일 검색 — 트랜잭션 **안**의 텍스트 찾기

표 위의 `프로파일 검색` 은 목록의 URL 이 아니라 **각 트랜잭션의 프로파일 내용**을 뒤진다.
SQL 문장, 바인딩 값, API 주소, 메서드 이름, 에러 메시지, 로그 메시지가 대상이다.

1. 먼저 차트에서 구간을 드래그한다 (검색 대상이 그 구간이다)
2. 검색어를 넣고 Enter
3. `1,650 / 2,101 흐는 중 · 적중 652건` 처럼 진행 상황이 보이고, 오래 걸리면 `중단` 할 수 있다

적중한 행에는 걸린 자리가 함께 뜬다 (`apicall-addr  shop-app:8081` 처럼 **어디서** 걸렸는지).
한 트랜잭션 안에서 여러 번 걸리면 `+N` 배지가 붙는다.

> 검색은 앱이 아니라 **콜렉터 쪽에서** 훑는다. 프로파일 전체를 화면으로 끌고 오지 않으므로 건수가 많아도 앱이 멈추지 않는다.

### 3.5.1 넓은 구간에서 찾기 (툴바 오른쪽 끝 `트랜잭션 찾기`)

프로파일 검색(3.5)은 **고른 구간 안**을 뒤진다. 그래서 「오늘 오전 내내 중 이 서비스만」은
구간을 잘게 나눠 여러 번 드래그해야 했다. 그걸 한 번에 하는 입구다.

**서버가 걸러서 보내 준다.** 다 받아서 화면에서 거르는 것보다 빠르다 — 창이 넓을수록 더:

| 창 | 다 받고 화면에서 거름 | 서버가 거름 |
|---|---|---|
| 2분 | 167ms | 45ms |
| 30분 | 1,116ms | 144ms |

- 조건: 구간 · 오브젝트 · 서비스 · IP · 로그인 · 설명 (+ 앱 자유 필드 text1~5)
- **그냥 치면 「포함」으로 찾는다.** `*` 를 직접 쓰면 그 자리만 아무 글자로 본다
- 오브젝트는 **하나만** 고를 수 있다 — 서버가 하나만 받는다. 「전체」로 두면 안 가린다
- 결과는 아래 트랜잭션 목록으로 들어간다. 행을 눌러 상세를 열고 프로파일 검색을 거는 건 그대로다

**서버는 한 번에 500건까지만 보낸다**(설정 `req_search_xlog_max_count` 의 기본값). 넘으면 **앱이 구간을
잘게 나눠 이어 찾는다** — 닿은 조각의 결과가 덮은 시간으로 폭을 짐작해 다시 묻고, 조각마다 500건 아래가
될 때까지 되풀이한다. 조각은 **넷씩 한꺼번에** 묻는다.

| 실측 (로컬 콜렉터) | 건수 | 요청 | 걸린 시간 |
|---|---|---|---|
| 1시간 · 서비스 하나 | 3,880 | 25 | 몇 초 |
| 1시간 · 조건 없음 | 38,201 | 167 | 약 4초 |
| 3시간 · 조건 없음 | 154,740 | 941 | 약 26초 |

- 찾는 동안 창 아래에 `모은 건수 · 훑은 % · 요청 수` 가 보이고, `멈추기` 를 누르면 그때까지 모은 것을 목록으로 보낸다
- 모두 **300,000건**까지 모은다(기본). **설정 → 트랜잭션 찾기 상한** 에서 10만 · 30만 · 50만 · 100만 중에 고른다 —
  올릴수록 메모리를 쓴다(100만 ≈ 370MB). 넘으면 멈추고 목록 머리에 「300,000건에서 멈춤 — HH:MM:SS 까지 찾음」 을 단다 —
  그 시각까지는 빠짐없이 찾은 것이고, 그 뒤로는 안 찾은 것이니 구간을 그 뒤로 잡아 다시 찾는다
- **1초 안에 500건이 넘게 걸리면** 그 1초는 500건만 담고 「빽빽한 구간은 1초에 500건까지만」 을 단다 —
  조건을 좁히면 다 나온다
- 넓은 구간·드문 조건은 콜렉터가 구간을 여러 번 훑는다. 몇 초 걸릴 수 있다

좁은 구간은 여전히 스캐터 드래그가 낫다 — 서버에 묻지 않고 받은 것에서 바로 고른다.

### 3.6 상세 패널

행을 누르면 오른쪽에 열린다.

**요약** — 응답시간, SQL 시간·건수, API 시간·건수.

**호출 흐름** — 이 요청이 거쳐 간 앱들. 토글이 둘이다.

| 토글 | 보이는 것 |
|---|---|
| `앱` | 앱 단위 시간 막대 — *어느 앱이* 느렸나 |
| `상세` | 사용자 IP → 서비스 → SQL·API 호출까지 내려간 나무 — *그 앱이 무엇을* 불렀나 |

`상세` 에서 `SQL` / `API 흐름` 체크를 끄면 **잎만** 사라진다. 이어진 앱은 남는다 — 흐름이 끊기면 안 되기 때문이다.
같은 대상을 여러 번 불렀으면 한 줄로 접히고 `×3` 처럼 횟수가 붙는다. 같은 SQL 50개가 50줄로 흩어지면 N+1 이 오히려 안 보인다.
다른 스레드로 넘어간 작업(비동기)도 그 스레드의 트랜잭션으로 이어 붙는다.

**프로파일** — 트랜잭션이 실제로 한 일을 순서대로.

- `목록` / `요약` 전환. 요약은 같은 항목을 묶어 횟수·합계·평균으로 보여주고 정렬할 수 있다
- 검색어가 걸린 스텝은 강조되고, 여러 곳이면 머리의 `‹ 1/2 ›` 로 옮겨 다닌다
- 긴 SQL 은 접혀 나온다. **`펼치기` 를 누르면 절 단위로 줄을 나눠 보여준다** —
  `select` · `from` · `join` · `where` · `order by` 가 각자 줄을 갖고 `and`/`or`/`on` 은 한 칸 들여쓴다.
  접힌 상태는 세 줄뿐이라 나누지 않는다(그러면 낱말 세 개만 보인다).
  **글자는 하나도 안 바뀐다** — 줄바꿈과 들여쓰기만 넣는다. 원문 한 줄은 마우스를 올리면 나온다
- **긴 본문은 종류를 가리지 않고 `전문 보기` 로 연다** — SQL 뿐 아니라 메시지 스텝의
  XML·JSON, API 호출 주소까지. 창에서 정렬해 보기(XML·JSON·SQL), 원문으로 되돌리기,
  줄 바꿈, 본문 안에서 찾기(Enter 로 다음, Shift+Enter 로 이전), 통째로 복사를 할 수 있다.
  SAP PO 의 `RECEIVER_PAYLOAD(XML)` 처럼 한 통이 통째로 실려 오는 스텝이 여기 해당한다.
  **자르는 것은 화면뿐이다** — 에이전트는 메시지를 길이 제한 없이 보낸다.
  다만 그 메시지를 **만드는 쪽**(플러그인·후킹)이 미리 잘랐다면 화면에서 되살릴 수 없다
- `THR` 스텝은 다른 스레드로 넘어간 자리다. 누르면 그 스레드의 트랜잭션이 열린다
- SQL 옆의 `~1행` 은 에이전트가 보고한 갱신 건수다. 읽기(SELECT)에는 안 붙는다.
  **물결(`~`)은 어림수라는 뜻이다** — 같은 연결로 UPDATE 를 잇달아 하면 앞 문장에 얹혀
  실제보다 크게 나온다(1행짜리가 `~2행`). 단독 실행에서는 정확하다
- `에이전트가 SQL 문장을 받지 못했습니다` 가 뜨는 자리가 있다. 자동 생성 키를 쓰는
  INSERT 는 드라이버가 문장 없이 PreparedStatement 를 만들어 에이전트가 문장을 못 얻는다 —
  콜렉터까지 문장이 오지 않아 복원할 수 없다. 이때 옆의 `1행` 이 유일한 단서다

**속성** — CPU, Heap, IP, TxID, GxID.
- CPU 가 `1ms 미만` 이면 정말 그만큼 쓴 것이다 — 에이전트가 늘 재지만 ms 로 버린다
- Heap 이 `수집 안 함` 이면 에이전트가 재지 않은 것이다. 에이전트 설정
  `profile_thread_memory_usage_enabled` 가 기본으로 꺼져 있다. 켜야 값이 오고, Y축 `Heap Used(KB)` 도 그때부터 뜻이 있다

### 3.7 여러 트랜잭션을 나란히 — 상세 탭

행을 여러 개 누르면 **탭으로 쌓인다.** 하나만 열려 있으면 탭 줄은 나오지 않는다.

느린 트랜잭션을 볼 때 실제로 하는 일은 «이건 왜 느리지» 가 아니라
**«정상인 것과 뭐가 다르지»** 다. 하나만 열리면 두 개를 번갈아 열어야 하고,
그 사이에 실시간 목록이 흘러가 방금 본 것을 다시 못 찾는다.

- 탭 이름은 **서비스명 + 시각 + 응답시간**이다. 같은 서비스를 두 개 열면 이름이 같아지므로 시각이 기준이 된다
- 같은 트랜잭션을 다시 누르면 탭이 늘지 않고 그리로 옮겨 간다
- `Ctrl+Tab` 으로 오간다. `Ctrl+W` 로 지금 탭만 닫고, `모두 닫기` 로 전부 닫는다
- **여덟 개까지** 열린다. 넘치면 가장 오래 안 본 탭이 닫힌다 — 지금 보는 것과 방금 본 것은 남는다

### 3.7.1 상세 안에서 찾기

프로파일 머리의 `이 안에서 찾기` 칸은 **연 트랜잭션 안에서만** 찾는다.
위쪽 검색바(3.5)는 «어느 트랜잭션에 그 SQL 이 있나» 를 묻는 자리라 목록이 바뀌지만,
여기는 이미 연 것 안에서 스텝을 짚을 뿐이다. `‹ 1/3 ›` 로 걸린 자리를 오간다.
칸을 비워 두면 위쪽 검색어를 그대로 따른다.

요약 표에서는 **줄을 누르면 목록의 그 스텝으로 간다.** 같은 쿼리가 여러 번이면
처음 나온 것으로 간다 — «그래서 언제 돌았는데» 가 다음 질문이기 때문이다.

### 3.8 프로파일을 파일로 남기고 다시 열기

**콜렉터는 오래된 트랜잭션을 지운다.** 어제 본 그 트랜잭션을 내일 다시 열려면
그때 남겨 둬야 한다. 남에게 보낼 때도 마찬가지다.

- **저장**: 상세 패널 오른쪽 위 `저장`. 지금 보고 있는 것 그대로 파일이 된다
- **열기**: XLog 툴바의 `저장본` → 목록에서 고른다. **접속하지 않아도 열린다**

파일은 `{데이터 폴더}/profiles/` 에 `20260830-141203_shop_order_z1pa9p0.json`
처럼 쌓인다(데이터 폴더는 설정에서 정한다. 기본은 실행 파일 옆). 창에 경로가
적혀 있고 `폴더 열기` 로 탐색기에서 연다 — **지우는 것은 폴더에서** 한다.

**서비스명·SQL·에러 문구가 풀린 채로 들어간다.** Scouter 는 이 문장들을 트랜잭션에
싣지 않고 해시만 보내며, 진짜 문장은 콜렉터의 사전에 있다. 해시만 저장하면 며칠 뒤
사전이 밀려났을 때 `[0x1a2b3c]` 만 남는다. 그래서 화면이 이미 풀어 둔 것을 같이 넣는다.

- 저장본 탭에는 시각 옆에 `· 저장본` 이 붙는다. 옆 탭들과 달리 **지금 흐르는 것이 아니다**
- 저장본은 다시 저장할 수 없다(`저장` 이 나타나지 않는다). 이미 파일이다
- 기존 Scouter 클라이언트가 남긴 `xlog.xlog`/`xlog.prof` 는 **열지 못한다.**
  그쪽은 해시가 안 풀린 와이어 포맷이라 사전 없이는 이름이 안 나온다

## 4. Counter 탭 — 지금 서버 상태

| 패널 | 답하는 질문 |
|---|---|
| 액티브 서비스 | 지금 **몇 건**이 어디에 몰려 있나 |
| 요약 | 무엇이 느렸나 · 어디서 실패하나 · 어느 호출자(IP)에서 왔나 |
| 토폴로지 | 외부 유입 → 애플리케이션 → 의존 자원 |
| 서비스 그룹 | 무엇이 들어오는가 / 서버가 견디는가 |
| 애플리케이션 · 호스트 · 커넥션 풀 | 카운터 차트 (오브젝트 종류별) |
| 호스트 · 5분 집계 | 실시간보다 긴 흐름 |

> **토폴로지가 "수집이 꺼짐" 으로 나오면** 에이전트 설정에서 `counter_interaction_enabled` 를 켜야 한다.
> 에이전트가 기본으로 수집하지 않는 항목이다.

### 4.1 볼 서버 고르기

그릴 서버는 **왼쪽 서버 목록에서 고른 것**이다 — 지금 XLog 탭의 고르기다(3.0). 구역(애플리케이션·호스트·커넥션 풀)은
고른 것 중 제 종류만 그린다. 한 타입에 열 대가 붙으면 선이 겹쳐 정작 보려던 한 대가 묻히므로
목록에서 좁힌다.

### 4.2 개별 · 서비스별 · 합계

구역 머리의 버튼으로 선을 어떻게 그릴지 고른다. 구역 단위다 — 카운터마다 다르면 나란히 놓고 비교하는 순간 틀린다.

| 버튼 | 선 | 답하는 질문 |
|---|---|---|
| `개별` | 서버마다 한 선 | 어느 서버가 이상한가 |
| `서비스별` | 서비스마다 한 선. 서비스에 안 속한 서버는 따로 한 선 | 어느 서비스가 견디고 있나 |
| `합계` | 고른 것 전부를 한 선 | 전체가 견디고 있나 |

- `서비스별` 은 서버 목록을 **서비스로 묶어 볼 때만** 나오고, 그때는 이것이 기본이다.
  ECS 에서 Task 4대짜리 서비스가 열 개면 개별은 40선이라 못 읽고, 합계는 서비스끼리 섞인다.
  Task 가 갈려도 서비스 선은 끊기지 않는다
- 접는 셈은 카운터가 정한다 — TPS 같은 양은 **합**, % 와 응답시간은 **평균**. 머리글에 적힌다
- CPU · Heap 처럼 더하면 뜻이 없는 카운터는 접지 않고 개별로 그리며 머리글에 `합계 없음` 이라고 적는다
- **바꿔도 지난 선이 남는다.** 받은 값을 그대로 들고 있다가 그릴 때 접기 때문이다

차트의 점선은 눈금이다 — 가로는 최댓값의 절반, 세로는 분이 바뀌는 자리(위에 `HH:MM`).

### 4.3 하루 누적 — 지난 날도 볼 수 있다

액티브 서비스 오른쪽의 누적 카드에서 **날짜를 고르면 그날 하루**(5분 × 288포인트)를
본다. 장애 다음 날 «어제 이 시간엔 어땠나» 를 묻는 자리다. `오늘` 버튼으로 돌아온다.

- 지난 날에는 **방문자 수를 내놓지 않는다.** 콜렉터의 방문자 커맨드에는 날짜가 없어
  오늘 값이 오기 때문이다 — 그날 것으로 읽히면 거짓이 된다
- 지난 날은 값이 더 이상 바뀌지 않으므로 다시 묻지 않는다(오늘만 1분마다 갱신)

## 5. Active 탭 — 지금 걸려 있는 것

다른 탭은 모두 **지나간 것**을 본다. 여기만 «지금 이 순간 무엇이 안 끝나고 있나» 다.

| 자리 | 무엇 |
|---|---|
| 게이지 | 실행 중 몇 건인가 (1초 미만 · 1~3초 · 3초 이상) · 가장 오래된 것 |
| 실시간 트래픽 | 최근 1분. **끝난 것은 채운 점, 실행 중인 것은 속 빈 동그라미** |
| 커넥션 풀 | 고른 WAS 의 풀 소진율 |
| 무엇을 기다리나 | 실행 중인 것을 리소스(쿼리·외부 호출)로 묶은 것 |
| 실행 중인 트랜잭션 | 느린 것부터. 줄을 누르면 스택, 쿼리를 누르면 전문과 바인드 값 |

### 5.1 목록이 비었는데 «한가한 것» 이 아닐 수 있다

목록은 **순간 스냅샷**이다. 2초마다 한 번 물으므로 **2초 안에 끝나는 요청은 한 번도
안 잡힌다.** 초당 수십 건이 잘 돌고 있어도 목록은 비어 보인다.

그래서 위에 트래픽 점을 같이 놓는다 — **점은 빽빽한데 목록이 비었으면 «빠르게 잘
돌고 있다»** 이고, 점도 없으면 그때가 정말 한가한 것이다. 점은 XLog 실시간 스트림에서
오므로 이 화면을 연다고 에이전트에 부담이 늘지 않는다.

- 끝난 점을 누르면 **XLog 탭의 상세**가 열린다 (탭이 따라 옮겨 간다)
- 속 빈 동그라미(실행 중)를 누르면 그 트랜잭션의 스택이 열린다
- 세로축은 창 안에서 가장 오래 걸린 값에 맞춰 올라간다. **쉽게 내려오지는 않는다** —
  매번 따라 내리면 점이 위아래로 춤춰서 못 읽는다

### 5.2 커넥션 풀은 따로 고르지 않아도 된다

WAS 를 고르면 **그 아래 풀을 앱이 찾아 값을 받는다.** 풀 오브젝트 이름이
`/호스트/앱이름/HikariPool-1` 처럼 부모 WAS 아래에 붙기 때문이다(에이전트가 그렇게 짓는다).

그런데도 «풀이 없다» 고 나오면 둘 중 하나다 — 화면이 어느 쪽인지 적어 준다.

| 화면 문구 | 볼 곳 |
|---|---|
| register-mbeans · jmx_counter_enabled 를 켜라 | 풀 오브젝트 자체가 안 올라온다 ([설정 가이드 §4](settings-guide.md#4-counter--visualize--토폴로지)) |
| 왼쪽에서 그 풀을 직접 고르라 | 풀은 있는데 이름이 WAS 아래로 안 붙는다 |

### 5.3 서버가 떴다 사라졌다 하면

화면 위에 **이유별로** 뜬다 — «연결을 못 얻어 못 물어본 서버» 와 «콜렉터가 비활성으로
보는 서버» 는 고칠 곳이 다르다. [설정 가이드 §3](settings-guide.md#3-active-탭-실행-중-트랜잭션) 참고.
못 받은 서버는 15초까지 **직전 값을 흐리게** 이어 보여준다.

## 6. Alert 탭 — 알림

콜렉터가 올린 알림이 쌓인다. 상단 알림 배지의 숫자를 누르면 이 탭으로 온다.
다른 탭을 보고 있어도 알림은 계속 모인다. 이 탭을 보고 있으면 읽은 것으로 쳐서 배지가 비워진다.
알림은 고른 서버와 상관없이 다 보이므로 이 탭에서는 왼쪽 서버 목록을 감춘다 — 다른 탭으로 가면 다시 나온다.

### 6.1 Task 교체와 서비스 장애 — 서비스로 묶어 보여 준다

ECS 처럼 Task 가 갈리는 곳에서는 재배포 한 번에 내려간 Task 마다 `INACTIVE_OBJECT` 가 온다.
진짜 장애(서비스가 통째로 내려감)도 같은 알림으로 오므로, 그대로 두면 둘을 가를 수 없다.
그래서 **같은 서비스의 Task 알림을 한 줄로 묶는다** (서비스는 2.1 의 「서비스로 묶기」 규칙으로 정한다).

| 표시 | 뜻 |
|---|---|
| `교체` (흐림) | 내려간 Task 마다, 그때 같은 서비스의 다른 Task 가 살아 있었다 — 배포·축소 |
| `장애` (빨강) · 살아 있는 Task 없음 | 내려간 것 중 하나라도 대신 받아 줄 Task 가 없었다 |
| … · 지금은 살아 있는 Task 가 있습니다 | 장애였고, 그 뒤 Task 가 다시 떴다 |

- 줄을 누르면 묶인 알림이 하나씩 펼쳐진다
- **배지는 교체를 세지 않는다.** 배포 한 번에 배지가 뛰면 배지를 안 보게 된다. 장애는 센다
- 「대신 받았다」 는 새 Task 가 **내려간 뒤 3분 안에** 떴거나 원래부터 살아 있던 경우다.
  옛 Task 를 먼저 내리고 새 Task 를 띄우는 배포(최소 정상 0%)도 이 안이면 교체로 본다.
  3분을 넘겨 뜬 것은 장애 뒤의 복구로 본다
- 같은 서비스의 알림이 5분 안에 이어 오면 한 묶음이다. 교체 직후 남은 Task 가 다 내려가면
  그 교체까지 한 장애로 묶인다 — 그때 숫자는 「교체 2 · 대신 받을 Task 없이 내려감 2」 처럼
  갈라 적는다. 정상 교체된 Task 까지 장애로 세지 않게
- 판정은 서버 목록이 갱신될 때마다(10초) 다시 한다 — 새 Task 가 늦게 뜨면 「장애」 가 「교체」 로 바뀐다
- 서비스 규칙에 안 걸리는 서버, 이 앱이 한 번도 못 본 서버의 알림은 지금처럼 한 줄씩이다.
  앱을 껐다 켜도 전에 본 Task 는 기록(3.1)이 남아 있어 묶인다

|---|---|
| 덤프 만들기 (스레드·액티브·스레드목록·힙 히스토그램) | 에이전트 **디스크에 파일이 생긴다.** 만든 뒤 해당 화면에서 본다 |
| 스택 샘플링 켜기(5분) / 끄기 | 켜 두면 주기적으로 스택을 모은다 |
| GC 실행 | **되돌릴 수 없다.** 그 순간 응답이 멈춘다. 한 번 더 눌러야 실행된다. 콜렉터가 결과를 알려주지 않으므로 Heap 카운터로 확인한다 |
| 힙 덤프 | 힙 크기만 한 파일이 디스크에 생긴다. 에이전트가 **10초에 한 번**으로 막는다 — 연달아 누르면 기다리라는 답이 온다 |
| 텍스트 캐시 비우기 | 해시가 이름으로 안 풀릴 때. 다음 전송부터 이름이 다시 올라온다 |

## 8. 설정 (⚙)

**데이터 디렉토리** — 설정 파일(`config.json`)과 로그 파일이 있는 곳. 현재 경로를 보여준다.

**SQL 바인딩 파라미터** — 프로파일의 SQL 은 값 대신 `?` 로 온다.

| 선택 | 결과 |
|---|---|
| 문장에 채워서 보기 (기본) | `where id=126` — 그대로 복사해 DB 에 붙일 수 있다 |
| 값을 따로 보기 | `where id=?` · 바인딩 `126` |

**단축키** — 목록을 그대로 보여준다.

**마지막 접속 정보** — 읽기 전용.

### 8.1 저장되는 것

껐다 켜도 그대로다. **바뀔 때마다** 남긴다 — 앱이 죽으면 «끌 때» 는 오지 않는다.

| 저장됨 | 저장 안 됨 |
|---|---|
| 패널 크기 (서비스 목록 · 상세 · 트랜잭션 표) | 검색 필터(서비스 포함 · IP) |
| 마지막에 보던 탭 (XLog / Counter / Alert) | 열어 둔 상세 탭 |
| 차트 설정 (Y축 · 범위 · Y 최대 · 무시 구간) | 고른 구간 |
| 글자 크기 · 언어 · SQL 바인딩 표시 | |

**필터를 저장하지 않는 이유:** 어제 걸어 둔 필터를 잊고 켜면 «왜 아무것도 안 보이지» 가 된다.
빈 화면과 «필터에 걸려 0건» 은 눈으로 구별이 안 된다.

---

### 8.2 껐다 켜도 남는 것

배치·차트 설정에 더해 **조회 조건**이 남는다 — 응답시간·에러만·고른 오브젝트·
서비스·IP 필터, 실시간/과거 모드, 카운터에서 고른 서버.

실시간/과거 **모드는 되살아난다** — 어디를 보고 있었는지가 그것이다.
다만 **구간(시작·끝 시각)은 남기지 않는다.** 어제 보던 «최근 1시간» 은 오늘 열면
남의 시간이라, 과거 모드로 떠도 구간은 **지금 기준으로 새로** 잡힌다.

**XLog 탭도 되살린다** — 탭마다의 이름·조건·고른 서버, 그리고 나눠 띄운 배치.

**열어 두었던 상세 탭은 되살린다.** 접속이 끝난 뒤 그 트랜잭션들을 다시 받아 연다.
다만 **콜렉터에서 밀려난 것은 못 연다** — 그건 고장이 아니라 보관 기간이 지난 것이고,
몇 개를 못 열었는지 아래에 한 줄로 알린다. 저장본 탭(파일에서 연 것)은 되살리지 않는다.
그건 `저장본` 창에서 다시 연다.

### 8.3 XLog 버퍼 상한

차트가 들고 있을 **최대 건수**다. 창(범위) 밖은 시간으로 지우고, 그래도 남는 것이
많으면 이 수에서 **오래된 점부터** 버린다.

| 고를 수 있는 값 | 대략 메모리 |
|---:|---:|
| **100,000**(기본) | 약 37MB |
| 300,000 | 약 111MB |
| 500,000 | 약 186MB |
| 1,000,000 | 약 371MB |

범위를 30분으로 두고 트래픽이 많으면 기본값이 먼저 걸린다 — 그때는 차트 아래에
«버퍼 상한 … 오래된 점부터 지웁니다» 가 뜬다. **뜨면 둘 중 하나다:** 범위를 좁히거나
이 값을 올린다. 올리면 그만큼 메모리를 쓴다.

바꾸면 열려 있는 화면에 바로 적용되고, **이미 받아 둔 점은 그대로 남는다.**

### 8.4 «점이 사라진다» 싶을 때

차트 오른쪽 위에 «데이터 시각이 이 PC 보다 N초 앞섭니다/뒤처집니다» 가 뜨면
**시계가 어긋난 것이다.** 차트의 오른쪽 끝은 이 PC 의 «지금» 이라, 그만큼 앞선 점은
창 밖에 놓이고 뒤처지면 오른쪽이 빈 채로 남는다. 스트림은 멀쩡하다.
콜렉터·에이전트 서버와 이 PC 의 시각을 맞추면 사라진다.

배지가 안 뜨는데도 비어 보이면 시계 문제가 아니다. 그때는 **버퍼 상한(7.3)** 과
범위(1·5·10·30분), 필터를 함께 확인한다.

## 9. 단축키

입력칸에 글자를 치는 중에는 동작하지 않는다 — 서비스 이름에 `1` 을 치는데 탭이 바뀌면 안 된다.
`Esc` 만 살아 있고, 그건 «이 칸에서 빠져나온다» 는 뜻이다.

| 키 | 하는 일 |
|---|---|
| `Esc` | 보고 있는 상세 닫기 |
| `Ctrl+F` | 프로파일 검색으로 이동 (XLog 탭으로 데려간다) |
| `Ctrl+1` ~ `Ctrl+5` | 탭이 놓인 순서대로 XLog / Active / Visualize / Counter / Alert |
| `Ctrl+W` | 상세 탭 닫기 |
| `Ctrl+Tab` / `Ctrl+Shift+Tab` | 다음 / 이전 상세 탭 |
| `Ctrl+,` | 설정 열기 |
| `Ctrl+R` | 실시간 ↔ 과거 |
| `F5` | 다시 조회 (과거 구간에서만) |

mac 에서는 `Ctrl` 자리에 `Cmd` 도 통한다.

## 10. 이럴 땐

| 증상 | 까닭 / 할 일 |
|---|---|
| 상세를 열었는데 `호출 흐름` 이 없다 | 그 요청은 한 앱에서 끝났다(GxID 가 없다). 흐름으로 그릴 게 없다 |
| 이름 대신 `0x1a2b3c` 같은 값이 보인다 | 이름 사전이 아직 안 올라왔다. `텍스트 캐시 비우기` 후 다음 전송을 기다린다 |
| 토폴로지가 비어 있다 | 에이전트의 인터랙션 수집이 꺼져 있다 (4장 참고) |
| 프로파일 검색이 0건인데 분명히 있다 | 검색 대상은 **드래그로 고른 구간**이다. 구간을 다시 잡고 검색한다 |
| 과거 조회 버튼이 안 눌린다 | 버튼 옆에 막힌 이유가 나온다 — 끝 시각이 시작보다 앞이거나, 시작이 미래이거나, 구간이 6시간을 넘거나, 하루를 넘어가는 경우 |
