## 2026-08-25 · CJFW 환경

### B-1. SQL 바인딩의 `@{n}` 형태를 못 채운다 — **처리됨**

프로파일의 SQL 이 `?` 가 아니라 `@{1}` `@{2}` … 로 온다. 지금 바인딩 채우기는
`?` 만 다루므로 **값이 하나도 안 붙는다.**

```sql
… left join fscps.cm_code_m_if b
     on a.menu_type_cd = b.comm_cd and b.comm_cl_cd = '@{1}'
   … where @{10} = @{11} and a.co_id = 'FP006'
쓰이지 않은 값 11개: '1', 'FP040', 'FP041', 'FP008', 'CB405', 'CB409',
                    'YYYYMMDD', 'YYYYMMDD', 1, 1, 'FW00'
```

- 값은 **제대로 오고 있다.** "쓰이지 않은 값 11개" 안내가 그걸 보여준다 —
  자리를 못 찾았을 뿐이다.
- `@{n}` 은 1-based 순번으로 보인다(`@{1}` ↔ 첫 값). 다만 **확인 필요**:
  같은 번호가 여러 번 나오는 경우(`@{10} = @{11}`)와 값 목록의 대응을 실물로 맞춰봐야 한다.
- 이 형태는 에이전트의 `EscapeLiteralSQL` 계열 설정에서 나온다. 로컬 테스트 환경에는
  나타나지 않아 예전에 **일부러 구현하지 않고 남겨둔 자리**다(확인할 방법이 없었다).
  이제 실물이 나왔으므로 구현 근거가 생겼다.
- 구현: `src/features/xlog/components/sqlBind.ts` (`?` 처리와 같은 자리).
  따옴표·주석 안의 `@{n}` 은 건드리면 안 되는 것도 `?` 와 같다.

**처리 결과**

테스트 환경에서 재현해 실물로 확인했다(F-49). JPA 만 쓰던 테스트 앱에서 이 모양이
안 나온 것은 **값이 전부 `?` 라 빼낼 리터럴이 없어서**였다(경로 때문이 아니다 —
처음에 «Statement 경로에서만» 이라고 적었던 것은 틀렸다. B-8 참조).
`/shop/lab/literal-sql` 엔드포인트를 추가해 그 모양을 만들었다.

```
sql   = … where p.category = '@{1}' and p.id > @{2} and @{3} = @{4}
param = "'fruit',100,1,1"
```

- 문자열은 **따옴표째** 갈아끼운다(안쪽만 바꾸면 `''fruit''`).
- `n` 은 순서가 아니라 **번호**다. 되풀이되거나 건너뛴다.
- 값이 없는 번호는 원문 그대로 둔다. 쓰이지 않은 값은 지금처럼 아래에 남는다.
- 재현: `live_sql_literal_escape`

### B-2. 에러라고 표시되는데 상세에서 에러가 안 보인다 — **처리됨**

원인은 앞의 두 갈래 중 **첫째**였다. 실측(F-50): 에러 트랜잭션 표본 10건이
**전부** 에러 해시를 스텝에 갖고 있지 않았다 — 서비스 계층에서 터진 예외라
실패한 SQL·API 스텝이 없다.

상세 패널은 에러 해시를 **프로파일 스텝에서만** 모아 사전을 조회했다.
그래서 XLog 에만 있는 에러는 조회 대상에서 빠지고 화면에 `[0xdb873d22]` 만 남았다.
사전에는 멀쩡히 들어 있었다 — 묻질 않았을 뿐이다.

`ApiCall`/`SQL` 스텝이 들고 있는 에러(`Read timed out` 등)는 잘 보였기 때문에
**어떤 에러는 보이고 어떤 건 안 보이는** 모양이 됐다.

- 고침: `useXLogDetail` 이 스텝 해시에 `xlog.error` 를 더해 조회한다.
- 재현: `live_service_error_not_on_steps`

### B-3. 텍스트 검색 속도 — 실환경 재측정 필요

로컬에서는 처리했다(`b827a0a`, 워커 8개 병렬).

```
로컬 실측: 7,356건 약 7초 (0.9ms/건) · 이전 2.8ms/건
```

**다만 실환경에서 같은 배수가 나오는지는 확인하지 않았다.** 로컬은 콜렉터가
같은 machine 의 컨테이너라 왕복이 0.2ms 다. 원격 콜렉터면 왕복 지연이 지배적이라
워커 수를 더 올리는 게 유리할 수 있다(현재 상수 `SEARCH_WORKERS = 8`).

### B-8. `?` 자리에 엉뚱한 값이 들어간다 — «파라미터가 자꾸 안 나온다» — **처리됨**

프로시저 호출 프로파일에서 자리 12개 중 7개만 차고 나머지가 `?` 로 남았다.
파고 보니 **원인이 둘**이었다.

**(1) 값 순서를 잘못 알고 있었다 (F-51 — 진짜 버그).**

한 문장에 리터럴과 바인딩이 같이 있으면 값 한 줄이 **«리터럴 먼저, 바인딩 나중»** 으로
이어 온다. 그런데 화면은 `?` 를 값 목록 **0번부터** 채우고 있었다.

```
sql   = … where p.category = '@{1}' and p.price between @{2} and @{3}
        and p.id > ? and p.name <> ? order by p.id limit @{4}
param = 'book',100,90000,5,30,'zzz'

고치기 전: … and p.id > 'book' and p.name <> 100 …   ← 리터럴 값이 ? 자리에 다시 들어갔다
           쓰이지 않은 값 2개: 30, 'zzz'              ← 진짜 값은 여기로 밀려났다
고친 뒤  : … and p.id > 30 and p.name <> 'zzz' …
```

손으로 쓴 SQL 은 코드값을 문장에 박고 사용자 입력만 `?` 로 넘기는 일이 흔하다.
실환경에서 «파라미터가 안 나온다» 가 **자꾸** 보인 것이 이것이다.

`@{n}` 의 최댓값이 곧 리터럴 개수이므로, 문장을 한 번 훑어 최댓값을 먼저 구하고
`?` 는 그다음부터 채운다(`scanSlots`).

**(2) 프로시저 OUT 파라미터는 애초에 값이 없다 (F-52 — 고칠 수 없는 쪽).**

스크린샷의 `{ CALL SP_USER_CHK(?, … 12개) }` 가 이 경우다. 에이전트는 `setXxx` 로
넘어온 값만 기록하고 `registerOutParameter` 는 걸지 않는다. IN 7개는 오고 OUT 5개는
**전선에 실려 오지 않는다** — 클라이언트가 채울 방법이 없다.

숨기지 않고 설명한다:
- 경고 문구에 «에이전트는 `setXxx` 로 넘어온 값만 기록합니다» 를 툴팁으로 붙였다.
- **아귀가 안 맞으면 온 값 한 줄을 그대로 같이 보여준다.** 채운 문장만으로는
  무엇이 왔는지 확인할 수 없다.

같이 알아낸 것: 파라미터 값은 `trace_sql_parameter_max_length`(**기본 20자**)에서
잘린 뒤 따옴표가 닫혀 온다. 긴 값은 **문장이 멀쩡해 보이는데 값이 다르다.**

- 구현: `src/features/xlog/components/sqlBind.ts` · `ProfileStepList.tsx`
- 재현: `/shop/lab/mixed-sql` → `live_sql_mixed_literal_and_bind`
- 화면 확인: 실물 트랜잭션에서 `p.id > 30 and p.name <> 'zzz'` 로 채워지는 것을 확인

### B-4. 글자가 너무 작다

밀도를 위해 작게 잡았는데 실사용에서 읽기 힘들다.

- 설정에 글자 크기(배율) 항목이 필요하다. 토큰이 `src/styles/tokens.css` 한 곳에
  모여 있으므로 루트 폰트 크기를 배율로 흔드는 방식이 맞다.
- 표·차트 축·프로파일 본문이 같이 커져야 한다 — 한 곳만 키우면 정렬이 깨진다.

### B-5. 요약 표의 `횟수 / 합계 / 평균` 이 무슨 수치인지 화면이 말하지 않는다

코드 기준으로는 이렇다(`types/summary.ts`, `components/summaryRows.ts`):

| 열 | 뜻 |
|---|---|
| 횟수 | 그 구간에 호출된 횟수(`count`) |
| 합계 | 소요 시간의 합, **밀리초**(`elapsed`). 콜렉터가 합계만 준다 |
| 평균 | `합계 / 횟수` — **앱에서 나눈 값**이다 |

문제는 **화면에 단위도, 어느 구간인지도 안 적혀 있다는 것**이다.
실제로 이런 행이 나온다:

```
saveSBSalesConfirmData   횟수 2   합계 5,275,590   평균 2,637,795   에러 2
```

ms 로 읽으면 평균 44분이다. 에러 2건과 함께이므로 타임아웃으로 설명될 수는 있지만,
**보는 사람이 그 판단을 하려면 단위가 적혀 있어야 한다.**

- 열 제목에 단위(ms)를 붙이고, 표 머리에 집계 구간(1시간/6시간/24시간)을 같이 보이게.
- 값이 비현실적으로 큰 행이 진짜인지도 한 번 실물로 확인할 것.

### B-6. 한국어/영어 전환과 옵션 설명 — **처리됨**

**한국어 원문을 키로 쓴다.** `t('실시간')` 처럼 부르고, 영어 사전에 없으면 한국어가
그대로 나온다. 키를 따로 만들면(`xlog.toolbar.realtime`) 사전에 없을 때 화면에 키가
뜨고, 문구를 고칠 때마다 사전을 찾아가야 한다.

- 설정 > 언어에서 한국어/English. `config.json` 의 `ui_language` 에 남는다.
- 문구 202개를 옮겼다. 빠짐은 **테스트가 감시한다**(`i18n/coverage.test.ts`) —
  화면에 새 문구를 넣고 사전에 안 넣으면 그 테스트가 깨진다.
- 언어를 바꾸면 화면 전체를 다시 그린다(`key={lang}`). memo 로 막아 둔 차트까지 확실히 바뀐다.
- 옵션 설명: Y축·범위·에러만에 툴팁을 붙였고, 설정 창의 각 항목에는 원래 있던 설명을 유지했다.

**Scouter 용어(TPS·XLog·Elapsed·GC)는 두 언어에서 같다.** 원본이 영어인 말이라
한국어 화면에서도 그대로 쓰고 있었고, 억지로 옮기면 오히려 못 알아본다.

### B-7. 좌측 서비스 목록 — 검색과 계층 접기 — **처리됨**

**묶는 기준은 `obj_type` 이다.** 실환경 화면에서 우측 라벨이 `CJFW` · `PRD-ORD` ·
`CJFW_QA` · `WayLo_QA` · `tomcat` · `datasource` · `reqproc` 였다 — 운영에서는 이 값이
시스템 이름으로 쓰이고 나머지는 종류로 남는다. 둘 다 "같이 보고 싶은 것끼리" 모인다.

이름의 경로(`/CJFW/PRD-FSCP/FDMKT-BO`)로 한 겹 더 나눌 수도 있으나 실물에서 깊이가
제각각이라 계층이 들쭉날쭉해진다. **한 겹으로 둔다.**

- 검색은 **전체 경로와 타입 둘 다** 본다. `CJFW`(시스템)로도 `BO`(이름)로도 찾는다.
  짧은 이름만 보면 `/PRD-FSCP/` 같은 중간 마디로 못 찾는다.
- **검색 중에는 접힘을 무시한다** — 찾은 것을 숨기면 검색이 아니다.
- 그룹 정렬은 이름순 **고정**. 살아 있는 수로 정렬하면 10초마다 목록이 춤춘다.
  그룹 안은 살아 있는 것 먼저 — 이건 에이전트가 죽고 살 때만 바뀌고, 그때는 신호다.
- 접힌 채로도 `살아있는 수/전체` 는 보인다.
- 타입 배지를 행마다 되풀이하지 않는다. 묶음 머리에 있으니 같은 말이 두 번이다.

- 구현: `src/features/xlog/components/agentTree.ts` (묶기·찾기 순수 로직) +
  `AgentSelectorPanel`
- **남은 확인**: 로컬 테스트 환경은 오브젝트가 5개라 161개에서의 체감은 못 봤다.

**뒤에 덧붙임 — 묶는 기준을 고를 수 있게 했다.**

B-7 에서 «이름의 경로로 한 겹 더 나눌 수도 있으나 깊이가 제각각이라 계층이
들쭉날쭉해진다» 며 미뤘던 것이다. 계층으로 **쌓지 않고** 한 마디를 묶음 이름으로 쓰면
깊이가 달라도 섞이지 않는다.

- `타입` — `obj_type` (기존)
- `그룹` — 이름의 **첫 마디(호스트)**. Scouter 이름 규칙이 `/{host}/{name}` 이고
  ASIS 도 같은 자리를 자른다(`ObjectNavigationView`)

처음에는 «마지막 마디를 뺀 앞부분» 으로 잡았다가 화면에서 보고 바꿨다 — 그러면 앱과
그 앱의 datasource 가 갈라져 **1개짜리 묶음만** 생겼다. 호스트로 자르니 한 대에 있는
것이 한자리에 모인다.
