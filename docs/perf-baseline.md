## 실측 (100,000건, mean)

| 항목 | mean | p99 | 가드 임계값 |
|---|---:|---:|---:|
| 좌표 변환 `dataToPixel` | **2.1 ms** | 3.6 ms | 200 ms |
| 충돌 감지 `PointMap.set+has` | **2.2 ms** | 3.2 ms | 200 ms |
| `XLogDataStore.addBatch` | **2.1 ms** | 4.2 ms | — |
| `XLogDataStore.prune` (절반 제거) | **1.5 ms** | 4.9 ms | 200 ms |

가드 임계값은 실측의 **100배**다. 과해 보이지만 의도적이다 —
빌드와 동시에 돌렸을 때 79ms 까지 튀어 한 번 실패했고, **흔들리는 테스트는 무시당한다.**
잡으려는 O(n²) 퇴화는 14,000ms 였으므로 70배 여유로도 확실히 걸린다.
정밀 측정은 `npm run bench` 의 몫이다.

## 버퍼 상한 (2026-08-31 실측)

저장소는 창(1~30분) 밖 데이터를 지우고, 그래도 남는 것이 많으면 **개수 상한**에서
오래된 것부터 버린다. 30분 창에서는 **55 TPS 만 넘어도** 상한이 먼저 걸려, 창은
30분인데 화면에는 그보다 짧은 구간만 남는다(현장에서 «중간 넘어가면 뒷부분이 갑자기
날아간다» 로 보고됨).

**기본 100,000(≈37MB), 설정에서 최대 1,000,000(≈371MB)까지.** 기본을 낮게 두는 이유는
메모리다 — 시간은 문제가 아니다(아래 표).

| 항목 | 30만 건 |
|---|---:|
| `addBatch` (한 번에 30만, 실사용에는 없는 크기) | 47.4 ms |
| `prune` | **1.0 ms** |
| heapUsed | **113 MB** |

메모리가 비용이라 상한의 상한을 100만으로 둔다. 그리고 **버릴 때 화면에 말한다** —
차트 아래에 «버퍼 상한 N건 — 오래된 점부터 지웁니다» 가 뜬다(N 은 지금 걸려 있는 값).
조용히 버리면 «데이터가 유실된다» 로 읽힌다.

## 가드가 진짜 잡는지 확인한 방법

임계값만 있고 검증이 없으면 **아무것도 보장하지 않는다.** 실제로 퇴화시켜 봤다.

| 변이 | 결과 |
|---|---|
| `prune` 을 `items.shift()` 반복으로 | **안 잡힘** — V8 이 fast-mode 배열의 shift 를 최적화한다 |
| `prune` 을 `items.slice(1)` 반복으로 | **잡힘** — 1.5ms → **14,000ms** |

> 첫 시도에서 가드가 통과한 이유는 더 심각했다. **테스트 데이터의 `endTime` 이
> 오름차순이 아니라 prune 루프가 즉시 종료됐다** — 즉 아무것도 측정하지 않고 있었다.
> 데이터를 실제 스토어와 같은 순서(오래된 것부터)로 고쳐서야 드러났다.
>
> **성능 테스트는 "통과"가 아니라 "퇴화시켰을 때 실패하는지"로 검증한다.**
