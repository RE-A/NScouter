# 테스트 설계 — 프로젝트 목표 기준

> **용도**: Claude 참조용. 프로젝트 목표를 "테스트로 증명 가능한 형태"로 번역한 설계.
> 실행 계층·명령은 [testing-strategy.md](testing-strategy.md), 프로토콜 사실은
> [verified-facts.md](verified-facts.md) 참조.

## 목표 → 검증 축

| 프로젝트 목표 | 검증 축 | 핵심 질문 |
|---|---|---|
| Scouter 지표 90% 이상 이관 | **A. 이관율** | 무엇을 옮겼는지 셀 수 있는가 |
| 옮긴 지표가 맞는 값 | **B. 정확성** | Scouter와 같은 값을 내는가 |
| Java 클라이언트가 느려서 교체 | **C. 성능** | 더 빠른가, 계속 빠른가 |
| 사용성·비주얼 개선 | **D. 사용성** | 개선이 회귀하지 않는가 |

축마다 테스트 성격이 다르다. 같은 방식으로 다루면 안 된다.

## A. 이관율 — 가장 먼저 풀어야 할 문제

### 문제: "90%"의 분모가 없다

현재 상태로는 90%를 측정할 수 없다. 분모(Scouter가 보여주는 것 전체)와
분자(NScouter가 보여주는 것)의 정의가 없기 때문이다.
**분모를 코드로 고정하지 않으면 이 목표는 영원히 "느낌"으로 남는다.**

### 설계: 인벤토리를 기계가 읽는 데이터로 만든다

**분모는 [asis/15-inventory-source-of-truth.md](asis/15-inventory-source-of-truth.md)에서 확정했다.**
소스 원본(`counters.xml`, `plugin.xml`, `MenuUtil.java`)을 직접 세었다.

```
카운터   host 24 + javaee 19 + datasource 3          = 46
기능     기본화면 6 + objType메뉴 10 + 오브젝트메뉴 14
         + XLog뷰 8 + 인터랙션 1                     = 39
────────────────────────────────────────────────────
합계 85개 → 90% = 77개
```

제외 대상과 근거는 15번 문서 5.3에 있다. **제외는 분모에서 빼는 게 아니라
`out-of-scope`로 표시한다.** 빼버리면 나중에 왜 뺐는지 알 수 없다.

> **초안(74)에서 바뀐 이유** — 초안은 ASIS **요약 문서**에서 뽑은 미검증 수치였다.
> 소스 대조 결과 카운터 46은 맞았으나 기능 28은 근거가 없었고,
> Interaction 카운터 10을 차트 카운터로 잘못 세었다(별도 기능 1로 정정).
> 덤으로 `plugin.xml`에 **구현체 없는 죽은 뷰 등록 8개**를 발견했다.
> **요약 문서의 수치를 분모로 쓰지 않는다.**

### 인벤토리 형식

`src/features/parity/inventory.ts` — 타입 있는 데이터로 둔다.

```ts
type ParityStatus = 'implemented' | 'partial' | 'not-started' | 'out-of-scope';

interface ParityItem {
  id: string;              // 'counter.javaee.TPS', 'view.xlog.realtime'
  category: 'counter' | 'view';
  name: string;            // Scouter 표시명
  status: ParityStatus;
  /** implemented / partial 이면 필수. 이 항목이 동작함을 증명하는 테스트 */
  evidence?: string[];     // ['L4:live_counter_stream', 'L1:CounterChart.test.ts']
  note?: string;           // out-of-scope 사유 등
}
```

### 이관율 테스트 (L1)

```
1. status가 implemented/partial 인데 evidence가 비어 있으면 실패
   → 자기신고 금지. 테스트 없이 "됐다"고 못 한다
2. evidence에 적힌 테스트 ID가 실제로 존재하지 않으면 실패
   → 죽은 참조 방지
3. out-of-scope 인데 note가 없으면 실패
4. 이관율 = (implemented + partial*0.5) / (전체 - out-of-scope)
   90% 미만이면 실패
```

**구현됨** — `src/features/parity/{inventory.ts, parity.test.ts}` (테스트 8건).

임계값은 ratchet 방식을 택했다. 목표(90%)를 처음부터 하한으로 두면 CI가 계속
빨개서 신호가 무뎌진다. `PARITY_RATCHET`을 현재 수준에 두고 기능을 옮길 때마다 올린다.
내려가면 테스트가 잡고, `PARITY_GOAL`(0.9)은 별도 상수로 남겨 남은 개수를 보고한다.

```
이관율 8.2% / 목표 90% — 대상 85개 중 70개 남음
```

`ratchet 상수가 실제 수준보다 뒤처져 있지 않다` 테스트가 있어서, 기능을 옮기고
상수 갱신을 잊으면 그것도 잡힌다.

## B. 정확성 — 골든 픽스처 계층을 추가한다

### 문제: 현재 두 계층 사이에 구멍이 있다

| 계층 | 속도 | 실물 정합성 |
|---|---|---|
| L3 (mock 서버) | 빠름 | **낮음** — ObjectPack 순서 버그를 통과시켰다 (F-4) |
| L4 (실서버) | 느림 + 환경 필요 | 높음 |

와이어 포맷 회귀를 빠르게 잡을 수단이 없다.

### 설계: L3.5 — 실서버 응답 바이트를 캡처해 고정

```
Test/scripts/capture_fixtures.py   실서버 응답을 그대로 파일로 저장
src-tauri/tests/fixtures/*.bin     캡처된 바이트
src-tauri/tests/fixture_parse.rs   픽스처를 파싱해 기대값과 대조
```

- 실물에서 뽑았으므로 mock과 달리 거짓 GREEN이 안 난다
- 환경 없이 돌아가므로 CI에서 매번 실행 가능
- 픽스처를 뜰 때 **어떤 조건에서 떴는지**(에이전트 구성, 부하 상태)를 함께 기록

우선 캡처 대상 (F-4와 같은 순서 버그 가능성이 남은 것부터):

| Pack | 현재 상태 |
|---|---|
| `PerfCounterPack` | **미검증** — 필드 순서 확인 안 됨 |
| `AlertPack` | **미검증** |
| `XLogProfilePack` / `Pack2` | 부분 검증 |
| `ObjectPack` | 수정 완료, 회귀 방지용 |
| `XLogPack` | 동작 확인됨, 회귀 방지용 |

Scouter 화면 규칙을 그대로 옮겼는지 확인하는 테스트. 근거는 ASIS 소스다.

## C. 성능 — 이 프로젝트의 존재 이유

### 문제: 비교 대상이 없으면 "빠르다"를 증명할 수 없다

두 가지 접근이 있다.

| 방식 | 장점 | 단점 |
|---|---|---|
| **(a) Java 클라이언트 실측 비교** | 목표에 직접 답함 | Eclipse 클라이언트 실행 필요. 환경 편차 큼. 반복 측정 어려움 |
| **(b) 절대 예산 + 회귀 방지** | 자동화 쉬움. 매 커밋 검증 | "자바보다 빠르다"를 직접 증명하진 않음 |

**제안: (b)를 기본으로 하고, (a)는 1회성 기준선 측정으로 한 번만 한다.**
(a)의 결과는 문서에 남기고, 이후 회귀 방지는 (b)가 맡는다.

### 성능 예산 (초안)

| 항목 | 예산 | 계층 | 근거 |
|---|---|---|---|
| 스캐터 렌더 50,000점 | **16ms 이내** | L1 | 60fps 1프레임 |
| 스캐터 렌더 100,000점 | 33ms 이내 | L1 | 30fps |
| PointMap 충돌 감지 100k회 | 10ms 이내 | L1 | O(1) 설계 확인 |
| XLog 파싱 10,000건 | 100ms 이내 | L2 | 1폴링 최대치 |
| 메모리 상한 | 100,000건 유지 시 증가 정지 | L1 | 무한 증가 방지 |
| 앱 초기 표시 | 3초 이내 | 수동 | Eclipse 대비 체감 |

architecture.md 9절에 이미 `OffscreenCanvas drawImage ~4ms/50k점` 수치가 있다.
예산 16ms는 여유가 있는 값이다.

### 성능 테스트의 함정

- **CI 머신 성능 편차**로 불안정해진다. 절대 시간 대신 **상대 비교**
  (예: `fillRect` 대비 `drawImage`가 빠른가)를 섞거나, 임계값을 넉넉히 잡는다
- 벤치는 유닛 테스트와 분리한다 (`npm run bench`). 매 커밋 실행하면 느려서 안 돌리게 된다

> **판단 필요**: (a) Java 클라이언트 기준선 측정을 실제로 할지.

## D. 사용성 — 자동화되는 것만 자동화한다

### 자동화 가능 (L1 상호작용 계약)

| 동작 | 기대 |
|---|---|
| 스캐터 드래그 | 선택 영역 내 XLog만 목록에 나온다 |
| 에러 필터 토글 | error≠0만 남는다 |
| Y축 모드 변경 | 좌표가 해당 모드 값으로 다시 계산된다 |
| 시간 범위 변경 | 윈도우 밖 데이터가 사라진다 |
| 점 클릭 | 해당 txid의 프로파일을 요청한다 |
| 연결 끊김 | 에러 표시 + 스트리밍 중지 |

**구현된 예**: `src/features/xlog/components/CounterChart.test.tsx` (5건).
Tauri `listen` mock 을 가로채 이벤트를 흘려보내고 DOM 을 확인한다.
`이벤트 → React 상태 → DOM` 구간이 여기서 덮인다.

> 이 테스트들은 처음부터 통과했다(기존 동작 검증). 그래서 **변이로 의미를 확인했다** —
> `CounterChart` 의 카운터 필터를 제거하니 `다른 카운터의 이벤트는 무시한다` 가 실패했다.
> 바로 통과하는 테스트는 이렇게 한 번 깨보지 않으면 아무것도 보장하지 않는다.

### 자동화 안 되는 것

미적 판단(색 조합, 여백, 폰트), 체감 반응성, 정보 배치의 합리성.
**Canvas 픽셀도 여기 속한다** — jsdom 에 2d 컨텍스트가 없어 선이 실제로 그려지는지는
확인할 수 없다.
**체크리스트로 남기고 자동화된 척 하지 않는다.**

#### 수동 확인 체크리스트 (카운터)

| # | 확인 | 실패 시 의심 지점 |
|---|---|---|
| 1 | 접속 후 dev 로그에 `start_counter_stream: objType=tomcat` | objType 해석 실패 (App.tsx `getObjectList`) |
| 2 | Counter 탭에 차트 4개, 각 제목이 `TPS (tps)` 형태 | `JAVAEE_COUNTERS` 표시명 |
| 3 | 제목 우측에 `· 2개 에이전트` | 이벤트 수신 (여기까지는 L1 로도 덮임) |
| 4 | **선이 실제로 그려짐** | `drawLines` / Canvas — **여기만 자동화 불가** |
| 5 | 부하를 끄면 선이 0 근처로 수렴 | 값 매핑 |

3번까지 통과하고 4번만 실패하면 문제는 렌더 루프에 한정된다.

### 시각 회귀 스냅샷 — 권장하지 않음

Canvas 픽셀 스냅샷은 GPU/폰트/안티앨리어싱 차이로 환경마다 깨진다.
깨진 스냅샷을 반복해서 갱신하다 보면 아무도 안 본다.
대신 **렌더 결과를 픽셀이 아니라 데이터로 검증한다** — 예: "이 좌표에 점이 찍혔는가"를
`PointMap.has(x, y)`로 확인.
